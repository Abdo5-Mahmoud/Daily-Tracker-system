## 3. Learning & Mentorship philosophy (The 3-Step Method)

The user explicitly requests a specific 3-step pedagogical approach for all new technical concepts:

1. **Step 1: Explain like to a 10-year-old**:
   - Use an intuitive, real-world everyday life analogy (e.g., from cooking, retail shop, physical objects).
   - Zero unnecessary academic jargon.
2. **Step 2: Explain like to a Software Engineer**:
   - The production logic: architecture, data flow, edge cases, and trade-offs.
   - Clean, practical TypeScript/React code snippets.
3. **Step 3: Immediate Micro-Quiz / Challenge**:
   - A short 1-2 question quiz or a small code puzzle/refactor to test and solidify understanding immediately before moving forward.

Preferred mentor behavior:
- Identify where the user's reasoning or code is wrong;
- Do not let the user fall into "meta-work" (over-documenting, over-planning, or getting trapped in prompt-engineering loops);
- Keep the user in the driver's seat of their own code;
- Maintain honest, constructive criticism over empty praise.

## 4. AI usage philosophy

The user is deliberately redesigning how they learn with AI.

Core principle:
AI should accelerate engineering work without becoming a substitute for engineering understanding.

The intended workflow is the **4-Phase Guided Implementation & AI-Auditing Protocol**:
1. **Flow Visualization & Mental Mapping First**: Before touching code, draw or articulate the journey of the request (Inputs -> Validation -> Upstream Service -> Errors -> Output).
2. **Guided Hands-On Draft**: The mentor guides the user to write the initial draft logic by hand using guiding questions, strictly banning copy-paste code dumping.
3. **Incremental Production Refinement**: Evolve the draft step-by-step to handle production edge cases, typing, and resilience.
4. **AI-Code Auditing Muscle**: Train the user's eye to rapidly inspect, understand, and spot bugs in AI-generated code (missing `await`, swallowed errors, loose typing).

The user specifically wants final code-review/performance-audit findings and the reasoning behind fixes preserved so they can later study and manually reproduce the engineering work.

The user is interested in prompt efficiency and reducing unnecessary context/tool usage. Project documentation should carry durable context; task prompts should focus on the current task rather than repeating the whole project.

## 18. Candid assessment — weaknesses / risks

These are working-pattern risks, not personal judgments.

### 1. Risk of over-engineering the learning system

The user spends significant thought on documentation structure, AI workflow, prompts, project architecture, and process design.

That can become productive engineering discipline, but it can also become **meta-work**: designing the system for learning instead of doing the actual learning.

Risk signal:
- creating or refining many documents before implementation;
- repeatedly redesigning the workflow;
- optimizing prompts/context before the underlying technical task is complete.

Countermeasure:
- treat documentation/process improvements as useful only when they remove recurring friction or preserve important knowledge;
- prioritize shipping and manual technical practice.

### 2. Risk of outsourcing implementation understanding to AI

The user is explicitly aware of this problem, which is good, but the risk remains.

If AI writes the difficult parts and the user only reviews the output superficially, the portfolio can become more advanced than the user's actual ability.

The planned manual reimplementation step is therefore important, not optional busywork.

### 3. Scope can become larger than the user's current level

Devfolio's intended architecture is ambitious: CMS behavior, authentication, persistence, structured content, media management, SEO, accessibility, AI evidence, and production-quality frontend behavior.

That is useful as a capstone, but attempting to perfect every subsystem at once can slow skill acquisition.

The correct approach is staged complexity, not reducing the ambition permanently.

### 4. The user can be pulled toward “best possible” instead of “good enough and verified”

The user's desire to find the best solution is valuable, but frontend work often requires choosing a sufficiently strong solution, shipping it, measuring it, and iterating.

Engineering maturity includes knowing when further optimization has low value.

### 5. There is a risk of confusing documentation quality with implementation quality

A very strong PRD/architecture document does not prove that the implementation is correct.

The user's strongest evidence will ultimately be:
- working systems;
- code they understand;
- measured behavior;
- justified decisions;
- bugs they can explain;
- trade-offs they can defend.
